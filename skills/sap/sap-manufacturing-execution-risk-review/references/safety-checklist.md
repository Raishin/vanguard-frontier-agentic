# Safety checklist — SAP Manufacturing Execution Risk Review

Use before making any manufacturing execution control remediation recommendation, especially for findings involving quality hold governance, backflush controls, DM/MES integration, or regulated manufacturing environments (GMP, FDA, ISO, AS9100).

## Non-negotiables

- Do not access, connect to, or request access to any live SAP PP system, SAP S/4HANA Manufacturing system, SAP Digital Manufacturing (DM/MES) system, SAP QM system, Fiori launchpad, SAP GUI session, backend RFC, or production manufacturing or MES database. This skill reviews artifacts only.
- Do not accept or request SAP logon credentials, RFC connection details, DM/MES API credentials, quality management system access, or direct manufacturing database connectivity.
- Do not release, modify, confirm, or close production orders. Do not post goods movements, adjust component consumption, issue materials, confirm routing operations, process quality usage decisions, or modify bill of materials or routing records. There is no production order release (CO02, CO01), no operation confirmation (CO11N, CO15), no MIGO goods movement, no component issue (movement type 261), no backflush trigger, no quality usage decision (QA11), no BOM modification (CS02), and no routing modification (CA02) in this skill's execution path. Recommendations always describe configuration and process design changes, not direct manufacturing actions.
- Do not approve, close, or recommend closing an unmitigated critical quality hold bypass finding in a regulated manufacturing environment. Only the quality manager and regulatory affairs team with appropriate authority can accept a product quality risk. State this explicitly when critical quality findings are identified. Do not authorize shipment or production continuation for affected lots without quality management sign-off.
- Do not recommend implementing configuration changes (order type parameter modifications, inspection type assignment changes, backflush configuration, MRP type changes) directly in a production SAP PP or QM system. All recommendations must first be tested in a development or quality system.
- Do not use memory alone to assert whether a specific manufacturing operation requires a quality inspection under GMP, FDA 21 CFR, ISO 13485, or AS9100. Quality inspection requirements must be grounded in user-provided quality plans, inspection type assignments, or regulatory compliance documentation.
- Do not assert that a backflush configuration is controlled without confirming that the authorization separation between goods movement posting and inventory quantity adjustment is verified in user-provided role exports.

## What people get wrong

- **Treating availability check at order release as a hard stop by default**: SAP PP availability check at production order release can be configured as a warning-only message rather than a hard stop. If the availability check result is a warning that allows the planner to override and release the order anyway, the control is effectively advisory, not enforcing. Verify whether the availability check result is a hard stop or an overridable warning.
- **Conflating backflush control with physical verification**: Automatic backflush at milestone confirmation posts component consumption based on BOM quantities, not actual physical counts. If actual consumption differs from the BOM quantity (scrap, yield loss, substitution), the inventory posting does not reflect reality. Backflush is not equivalent to a physically verified goods issue.
- **Overlooking inspection lot creation gaps for in-process inspection**: Inspection type 04 (in-process inspection) requires both the inspection type to be active in the material master QM view and the relevant production routing operation to be flagged for inspection. If the material master has inspection type 04 active but the routing operations are not flagged, no inspection lots are generated during production execution — the in-process quality control is silently missing.
- **Assuming DM/MES integration is clean because production orders appear complete in SAP**: SAP PP production orders can be marked as technically complete (TECO) by a planner even when DM/MES operation confirmations are missing or integration errors have occurred. A TECO status does not prove that all DM/MES confirmations were received and posted correctly in S/4HANA.
- **Missing MRP horizon firming zone impact on procurement**: The MRP firming horizon determines the boundary within which planned orders are protected from automatic rescheduling. If the firming horizon is too short relative to the supplier lead time, MRP will generate rescheduling proposals that conflict with open purchase orders — creating procurement confusion and potential over-ordering. Firming horizon design is a procurement control, not just a planning preference.
- **Overlooking quality notification closure as a prerequisite for production order completion**: In some manufacturing quality processes, open quality notifications (defect reports, non-conformance reports) should block production order completion until resolved. If production orders can be technically completed (TECO) while open quality notifications referencing those orders remain unresolved, the quality issue may not be formally closed before the order is archived.
- **Ignoring regulated environment requirements for electronic signatures on usage decisions**: FDA 21 CFR Part 11 and similar regulations require electronic records and electronic signatures for quality-critical decisions in pharmaceutical and medical device manufacturing. A quality usage decision in SAP QM that does not meet electronic signature requirements in a regulated environment is a regulatory finding, not merely a best practice gap.

## When to push back

- Push back (and escalate immediately) when a quality hold bypass is found in a regulated manufacturing environment (GMP, FDA 21 CFR Part 11, ISO 13485, AS9100) — do not proceed with other recommendations until this is escalated to the quality manager, regulatory affairs team, and internal audit team. Affected lots must be reviewed before release.
- Push back when the user asks to confirm manufacturing control compliance from memory alone without providing configuration exports, production order status reports, MRP exception data, or QM inspection lot summaries.
- Push back when the request requires live SAP PP, DM/MES, or QM system access (SAP GUI session, RFC call, Fiori OData API, direct manufacturing database query) — state clearly that live inspection is out of scope and ask the user to supply the relevant exports or summaries.
- Push back when asked to release production orders, confirm operations, post goods movements, process quality usage decisions, or modify BOM or routing records — this is an absolute boundary and must be refused in all circumstances.
- Push back when asked to approve or close a manufacturing audit finding or quality non-conformance without quality management and audit team authorization — this skill is advisory only.
- Push back when DM/MES integration errors are identified but the user cannot provide integration monitor status reports or production order reconciliation data — do not accept that DM/MES integration is clean without evidence.
- Push back when a regulated environment quality bypass finding is identified and the user requests an assessment of compliance status — regulatory compliance determination requires direct engagement with the quality management and regulatory affairs team, not an advisory-only review.

## Evidence labels

- `documentation-based` — grounded in SAP Production Planning and Control, SAP S/4HANA Manufacturing, SAP Digital Manufacturing (DM/MES), SAP Quality Management, or SAP Help Portal PP/QM documentation
- `user-provided evidence` — production order status reports, MRP exception aging reports, capacity utilization summaries, QM inspection lot reports, DM/MES integration status exports, backflush configuration summaries, BOM and routing change logs, or written descriptions provided by the user
- `inference` — derived reasoning not directly confirmed by official docs or user evidence; must always be labeled as such
