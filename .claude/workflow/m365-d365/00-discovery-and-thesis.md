## 1. Phase 0 Discovery — Repo Conventions Observed (all E2)

### 1.1 Agent Directory Layout

| Fact | Detail |
|------|--------|
| Root path | `agents/<provider>/<name>-agent/` |
| Required files | `metadata.json`, `AGENT.md`, `harnesses/` (7 adapter files) |
| Harness adapter filenames | `codex.toml`, `copilot.agent.md`, `claude-code.agent.md`, `cursor.agent.md`, `gemini.agent.md`, `kiro-ide.agent.md`, `kiro-cli.agent.json` |
| `metadata.json` → `harness_variants` | Maps harness id → relative path to adapter file |

**`metadata.json` required fields (E2):**

| Field | Constraint |
|-------|-----------|
| `id` | string |
| `name` | string |
| `version` | semver `x.y.z` |
| `type` | `"agent"` |
| `provider` | closed enum — see §3 |
| `harnesses` | array |
| `summary` | string, ≥20 chars |
| `source_type` | `"original"` \| `"adapted"` \| `"reference-only"` |
| `official_docs` | array of `{uri}`, ≥1 item |
| `security_notes` | string, ≥20 chars |
| `last_verified` | `YYYY-MM-DD` |
| `path` | string |

**Optional fields:** `companion_skills[]`, `execution_tier` (`static-review` \| `read-only-runtime` \| `mutating-runtime`), `lifecycle`, `harness_variants{}`

### 1.2 Skill Directory Layout

| Fact | Detail |
|------|--------|
| Root path | `skills/<provider>/<name>/` |
| Required files | `SKILL.md`, `metadata.json` |
| Optional files | `references/*.md` — skill-specific, NOT a fixed 5-file template |

**`SKILL.md` frontmatter required fields (E2):**

| Field | Constraint |
|-------|-----------|
| `name` | kebab-case |
| `description` | 50–1500 chars |
| `allowed-tools` | space-separated string or YAML array |
| `metadata.author` | string |
| `metadata.version` | string |
| `metadata.updated` | optional |
| `metadata.category` | optional, closed enum — see §3 |

### 1.3 Maestro Pattern

- A maestro AGENT reads its companion maestro SKILL.
- The skill's `references/workflow-and-output.md` IS the routing table — not a narrative doc.
- Maestro never answers directly. Routes only.
- Max 4 parallel specialists per routing decision.
- Live-guard agents (mutating-runtime tier) require explicit human confirmation + blast-radius statement before dispatch.
- Routing is validated by `tests/validate-maestro-routing.py` against `tests/fixtures/<provider>-maestro-routing/`:
  - `taxonomy.json` — `domains{keywords, agent}`, `live_guards[]`, `gate_mode`, `live_guard_intent` regex, `parallel_threshold`
  - `inputs/NN.json` + `expected/NN.json` — fixture pairs
- Fixtures are generated by `tests/_generate_maestro_routing_fixtures.py` reading `catalog/agents.json` filtered by provider.

### 1.4 Catalog & Integrity

| Concern | Mechanism |
|---------|-----------|
| Agent/skill catalogs | `catalog/agents.json`, `catalog/skills.json`, `catalog/skill-manifest.json` — GENERATED, not hand-edited |
| Regenerate | `npm run manifest:write:all` |
| SHA256 asset integrity | `catalog/asset-integrity.json` via `python3 tests/validate-asset-integrity.py --write` |
| Validation gate | `npm run validate` — 19+ gates; must pass before commit |

**Validation gates include (E2):** `validate:catalog`, `validate:agent-schema`, `validate:skill-schema`, `validate:maestro-routing`, `validate:kiro-powers`, `validate:asset-integrity`, `validate:readme-counts`, `validate:install-coverage`, `validate:multi-harness-marketplace`, `validate:plugin-manifest`, and others.

### 1.5 DRY / Count Rules

- Never hardcode counts, versions, or provider/role lists in documentation.
- After any catalog change run: `npm run readme-counts:write`, `npm run docs-data:write`, `npm run plugin-manifest:write`, `npm run cursor-plugin:write`, `npm run kiro-powers:write`.
- Or all-in-one: `npm run manifest:write:all`.

### 1.6 Cross-Functional Protocols

- Live in `skills/cross-functional/` with `provider: "generic"`.
- Examples: `salesforce-routing-protocol`, `legal-hr-case-capsule`.
- Microsoft protocols (e.g. M365 change-freeze, D365 release-gate) belong here with `provider: "generic"`.

## 2. Brutal Executive Thesis (E0/E2)

The brief scoped this work as roughly 5 maestros + 30 specialists + 15 protocols + 24 skills — approximately 74 assets in a single sprint. That is not how this repo works. Every asset touches the catalog, the asset-integrity SHA store, the provider enum in at least six separate files, the Kiro powers generator, the plugin manifests, and the maestro routing fixture suite. A big-bang PR shipping 74 assets simultaneously will fail validation on the first gate, produce a diff too large to review meaningfully, and create a merge-conflict surface that blocks every other team contribution for its entire lifetime in review. The answer is gated waves, each independently shippable and validation-green.

The deeper risk is not insufficient agent count — it is agent sprawl masking weak routing. A maestro that cannot distinguish an Exchange mail-flow incident from a Power Automate governance request is worse than no maestro at all. Routing tables must be grounded before specialist agents are written, not after. Phase 1 is therefore taxonomy-first: define the routing taxonomy, validate it against the fixture framework, then build specialists into it.

Every Microsoft product claim in the brief — certification exam IDs, Copilot governance controls, Success by Design gate names, Power Platform CoE Starter Kit capabilities, D365 Finance release cadence — was written from memory against a moving Microsoft product surface. Microsoft Learn content changes quarterly. None of these claims are E3-verified in this plan. They are E3/E4 `(verify)` throughout. Build phases must open with a Context7 + Microsoft Learn pass to ground each claim before writing agent instructions that ship to production tenants.

The provider enum does not contain `microsoft`. This is not a documentation gap — it is a hard schema rejection. Six separate files enforce the closed enum. Every asset the brief proposes would fail `npm run validate` immediately. Provider registration is not a footnote; it is the first code change and it gates everything else. There is no Phase 1 without a green Phase 0 that ships provider registration alone.

Finally: the brief's 5-file references template applied to 24 skills produces 120 reference files, most of which would be boilerplate filler. This repo's existing skills use 3–4 skill-specific reference files tailored to actual workflow decision points. Padding every skill to hit a template count adds noise, inflates the diff, and degrades the signal quality that validators and reviewers rely on.

## 3. Brief-vs-Repo Corrections — THE MOST IMPORTANT SECTION (E2)

| # | Brief claim | Why it is wrong | Fix |
|---|-------------|-----------------|-----|
| 1 | `provider: microsoft` | `microsoft` is absent from the closed provider enum in: `schemas/agent.schema.json`, `schemas/skill.schema.json`, `schemas/rule.schema.json`, `schemas/mcp-reference.schema.json`, the `ALLOWED_PROVIDERS` set in `tests/validate-catalog.py`, the `PROVIDERS` object in `scripts/generate-kiro-powers.mjs`, and the taxonomy in `scripts/generate-docs-data.mjs`. Assets with this provider fail `validate:catalog` and `validate:agent-schema` immediately. | Phase 0 task: register `microsoft` (or `vanguard-microsoft`) as a provider in all six enforcement points before writing a single agent or skill. `generate-plugin-manifest.mjs` and `generate-cursor-plugin.mjs` derive providers dynamically from catalog — no edit needed in those files. |
| 2 | `category: microsoft` | Not a valid category value. Category is a closed enum: `security`, `platform`, `data`, `finops`, `ai`, `delivery`, `observability`, `compliance`, `resilience`, `networking`, `storage`, `database`, `compute`, `architecture`, `messaging`, `serverless`, `cost-management`, `operational`, `generation`, `devsecops`, `finance`. | Map each Microsoft skill to the nearest existing category. Examples: M365 security posture → `security`; D365 Finance → `finance`; Power Platform CoE → `platform`; Copilot Studio → `ai`. |
| 3 | `domain: m365\|d365\|...` | No `domain` field exists in `schemas/skill.frontmatter.schema.json` or `schemas/agent.schema.json`. The field would be silently ignored at best, schema-rejected at worst. | Drop `domain` entirely. Routing differentiation belongs in the maestro taxonomy.json and in agent `summary` text, not in a non-existent schema field. |
| 4 | `allowed-tools: Context7` | Real `allowed-tools` values in existing skills are tool names like `Read`, `Grep`, `Glob`, `Edit`, `Write`, `Bash`, `WebFetch`, `WebSearch`. MCP server access (`Context7`, `Microsoft_Learn`) is not declared in frontmatter `allowed-tools` in the same way — it is harness-level configuration. Whether MCP tool names are valid `allowed-tools` values must be confirmed. **E2 (verify against schema and existing skills before writing any SKILL.md with MCP tool names.)** | Audit `schemas/skill.frontmatter.schema.json` `allowed-tools` definition and cross-check against 3–4 existing skills that use MCP. If MCP names are invalid, remove them from `allowed-tools` and document MCP dependency in `SKILL.md` body only. |
| 5 | Rigid 5-file references template for every skill | The brief mandates `official-sources.md`, `workflow-and-output.md`, `safety-checklist.md`, `business-impact-kpis.md`, `role-certification-map.md` for every skill. Existing skills use 3–4 skill-specific files. Applying this universally = 24 × 5 = 120 reference files, majority boilerplate. | `workflow-and-output.md` is REQUIRED for any maestro skill (it is the routing table). `official-sources.md` is strongly recommended. `safety-checklist.md` is required for any mutating-runtime skill. `business-impact-kpis.md` and `role-certification-map.md` are OPTIONAL — include only where the content is materially different from a one-liner. |
| 6 | `powers/` directory assumed to exist for new provider | A new provider needs `powers/vanguard-microsoft/POWER.md`. This file is auto-generated by `npm run kiro-powers:write` after the generator (`scripts/generate-kiro-powers.mjs`) is updated to include `microsoft` / `vanguard-microsoft` in the `PROVIDERS` object. | Add provider entry to generator first; run `kiro-powers:write`; commit generated file. Do not hand-author `POWER.md`. |
| 7 | Maestro routing fixtures assumed automatic | The brief treats routing validation as a post-hoc check. In reality, `tests/fixtures/<provider>-maestro-routing/` must exist and be populated before `npm run validate` will pass. Fixtures require `taxonomy.json` + `inputs/` + `expected/` and are generated by `tests/_generate_maestro_routing_fixtures.py`. | Provider registration must include seeding the fixture directory. Fixture generation is part of Phase 0 / Phase 1, not a final-step cleanup. |
| 8 | Asset integrity assumed self-updating | The brief does not mention `catalog/asset-integrity.json`. Every new file in tracked paths changes the SHA store. Forgetting to run `python3 tests/validate-asset-integrity.py --write` after any wave causes `validate:asset-integrity` to fail for all subsequent waves. | Each wave's completion checklist must include: `python3 tests/validate-asset-integrity.py --write && npm run manifest:write:all && npm run validate`. |
| 9 | Companion skill links not declared | The brief lists companion skill pairings in prose. The schema requires `companion_skills: [<skill-id>]` in agent `metadata.json` for the pairing to be machine-readable and validated. | Every agent `metadata.json` for agents that have a companion skill must declare `companion_skills`. This is especially critical for maestro agents whose routing skill is their primary function. |
